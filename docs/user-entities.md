# 人物・研究室／組織とオーナー資格

Usersを共通の主体として使用し、Books.owner_idの既存の参照を維持する。

- `entity_type`: `person`（人物、既定値）／`organization`（研究室・組織）。
- `can_own_books`: `0`（指定不可、既定値）／`1`（指定可）。
- 人物・組織とも、資格を有効にすればOwnerに指定可能。
- 貸出・返却は人物のみ。組織名しか一致しない名前検索は409を返し、
  その組織名で人物を自動作成しない。同名の人物が存在する場合は人物を選ぶ。
- 所有している本が残る主体は資格を解除できない。先に各本のOwnerを変更・解除する。
- 貸出・返却履歴に登場する人物は組織へ変更できない。別の組織レコードを作成する。
- 既存仕様との互換性のため、APIの返却者未指定（NULL）は引き続き許容する。

## 操作

トップページのハンバーガーメニュー「人物・組織 / 貸出状況」から
`/users/manage`へ移動する。専用ページで人物・組織の追加、名前・種別・
Owner指定可否の変更、削除を行う。所有する本または貸出・返却履歴がある
主体は削除できない。削除前に確認ダイアログを表示する。

同ページで現在の貸出状況を確認でき、全履歴（返却済みを含む）へ切り替えられる。
一覧は25件ずつ表示し、本・借り手・貸出日・返却期限・返却状態／返却者を表示する。
本のリンクからBook manageに移動できる。

Book manageではOwner選択だけを行い、Add / Update Bookで本への割当を保存する。
候補管理フォームは置かない。候補設定の保存だけでは本のOwnerは変更しない。

Users APIのPOST/PUTも`entity_type`と`can_own_books`に対応。
PUTで省略した属性は保持し、貸出時の通常のユーザー作成は「人物・指定不可」となる。
適格性・貸出主体の制約はDBトリガーでも検証し、同時更新や直接書込みによる不整合を防ぐ。
この属性は所有主体の分類であり、ログインや管理者権限ではない。
候補設定APIも既存アプリと同じアクセス制御に従う。新しい認可機構は追加していない。

## 既存DBの移行

アプリ起動時には自動移行しない。新しいコードを稼働させる前に、対象DBを明示して実行する。
新規DBは通常の初期化で対応する。

```sh
python -m scripts.migrate_user_entities /path/to/library.db
python -m scripts.migrate_user_entities /path/to/library.db --apply
```

指定なしは読取り確認のみ。`--apply`はSQLite Backup APIでバックアップを作成してから、
トランザクション内で列追加・既存Ownerの資格有効化・トリガー作成を行う。
既存ユーザーは全員人物とし、現在のOwnerだけ資格を有効にする。
未指定の所有関係はそのまま保持する。不正な既存Ownerや外部キー違反がある場合は中止する。
再実行しても変更済みの資格は初期化しない。
バックアップ先は既定でDBと同じ階層の`backups/user-entities/`。
必要なら`--backup-dir`で変更できる。

本番では先にサービスを停止し、バックアップを確保してこの移行を実行し、
新コードで再起動・動作確認する。本番への反映は別のデプロイ作業として行う。
コードを旧版へ戻してもDBトリガーは残るため、旧版の所有者・貸出処理と互換とは限らない。
DB復元が必要ならサービスを停止し、移行後の更新を退避・確認してから実施する。
新しい利用者更新を失う可能性があるため、バックアップを無条件に上書き復元しない。
