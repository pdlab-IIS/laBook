# Slack認証を使うさくら中継への移行手順

更新: 2026-09-21。本書を移行計画の正本とする。Google認証・Notion認証・Slack Connect対応は今回の対象外。
Slack単独デモ・RPi署名入口の実HTTP試験に加え、PHP認証/中継と画面prefix対応を実装済み。
新認証入口の実SSO、ngrok経由の結合試験、本番切替は未実施。
個別のドメイン、IP、SSH接続先、実ワークスペースID、鍵は記載せず、非公開設定から取得する。
再開用の短い記録は [引継ぎ要約](slack-migration-handoff.md) を参照。

## 1. 移行後の構成と維持するもの

```text
ブラウザ
  → 所有ドメインのHTTPS /labook/
  → さくらPHP: Slackログイン・セッション・利用権限・CSRF確認
  → 固定ngrok上流へHTTPS + 要求ごとのHMAC署名
  → ngrok: 実測したさくら送信元IPのみ許可
  → RPi: 署名・時刻・nonce検証 → laBook
```

- ngrokのOAuthをさくらのSign in with Slackに置き換える。ngrok自体の転送量等の制限がなくなるわけではない。
- IP制限とHMACを併用する。共用サーバーの送信元IPだけで自分のアプリを識別しない。
- WordPressのファイル・DB・テーマ・プラグイン・生成ブロック・全体PHP/WAF設定は変更しない。
- 共有するルート.htaccessの変更は、本番切替時の旧laBook用Redirect 2本の置換と専用ブロック追加に限定する。他サービスのルールは維持する。
- 準備中は現行laBook、既存ngrok endpointとOAuthを維持する。試験は別プロセス・別DB・別鍵・別通信経路で行う。
- 現在のlaBook Usersは所有者・借用者データ。Slackログイン利用者とメールだけで自動結合しない。業務機能やNotion連携機能の変更は今回含めない。

## 3. Slack認証の採用方針

対象は、指定した単一ワークスペースでSlack OIDC認証が成功する利用者。
Slack Connect外部参加者への許可拡張とゲスト固有の対応は保留し、追加のBot権限は今回の必須条件にしない。
公開の「ID確認モード」は本番へ持ち込まず、expected_team_idの欠落・空値・不正値は起動時に拒否する。

### ログイン入口

- 第一候補は成功したworkspace-entry方式。固定したワークスペースのHTTPSトップから、相対 `/oauth?...` を認証再開先として大学SSOへ進む。
- この入口はSlack内部の転送方式を利用する実験的実装で、公開OIDC仕様により保証されたものではない。本番相当のcallbackで再試験し、Slack側の変更で壊れた場合に切り替えられるよう入口生成を分離する。
- 代替は公開OIDC入口でteamを省略する選択方式。state・nonce・署名・Workspace IDの検証はどちらも同じにする。
- team指定ありは新規ログイン時に失敗、応答形式指定を外すだけでも失敗、team省略と手入力は成功。teamを戻すだけの修正は採用しない。
- 入力省略版では、開始POSTに同一サイトの200応答を返し、即時meta refreshで固定Slack URLへGET遷移している。CSPを広く緩和せず、このブラウザ挙動も本番入口で検証する。
- 本番の入口選択は非公開設定で固定する。デモのflowクエリ切替・確認モード・試験表示は本番に公開しない。

### 本人確認と利用許可

- scopeはopenid profile email。既存のRS256署名、issuer、audience/azp、exp/iat、nonce、subject/user ID、at_hash検証を引き継ぐ。鍵キャッシュ・更新時の挙動と依存ライブラリの監査も整える。
- 署名検証後のteam_idが非公開のexpected_team_idと完全一致することを必須にする。メールドメイン・表示名・ブラウザ指定teamを根拠に許可しない。
- 主体はSlack issuer・team_id・user_idの組で識別する。RPiには署名した主体識別子だけを渡し、Slackコード・IDトークン・アクセストークンを転送しない。
- callbackはGET/POSTに対応し、5分・一回限りのstateをブラウザ相関Cookieと照合する。相関CookieはSecure/HttpOnly/SameSite=None、本体セッションは別名・別保存先でSameSite=Lax。
- 認可コード・トークンは保存・表示しない。GET callbackはホスティング側アクセスログにコードが含まれ得るため、ログ取得・共有時にクエリを除去する。復帰先に認証パラメータを残さない。
- デモの署名検証成功は継続在籍確認ではない。初期運用ではセッションごとのOIDC再認証とローカル失効で扱い、Slack退会・停止の即時反映は保証しない。即時失効を要件にする場合のみ別工程で管理API連携を設計する。

### セッションとCSRF

- 本番専用Cookie名、www外の保存先、Secure/HttpOnly、Domain省略、Path=/labook/、strict_mode。ログイン成功時にID再発行。
- 初期案は無操作30分・絶対60分。毎要求で期限、現在の許可team、設定世代・失効情報を確認する。設定変更後に古い許可結果だけで通さない。
- 認証用login/callback/session/logoutはPHPで終端し、RPiへ送らない。ログアウトはCSRF付きPOSTでlaBookセッションだけを失効させる。
- HTMLの未認証GETはログインへ。APIの未認証は401 JSON、許可不足は403。更新操作をログイン後に自動再送しない。
- 復帰先は/labook/配下の安全な相対GET URLに限定し、棚コードとクエリを維持する。外部URLや制御文字を拒否。
- POST/PUT/PATCH/DELETEにCSRFトークンとOrigin検査を適用。HMACの秘密鍵とCSRFトークンを混同しない。
- 認証情報を読み出したら上流通信前にPHPセッションロックを解放し、画像/APIの並列要求を直列化しない。

## 4. 実装・並行試験の順序

### A. 接続と非公開設定の整理

1. 非公開配備設定からさくら情報を読み、RPiの現在の接続先を確認する。秘密値を会話やログへ出さない。
2. 現行サービスの実行プロセス・DB・バックアップ・ngrokポリシーを読み取り確認する。サイト全体の同期や設定上書きをしない。
3. Web PHPの外向きIPを再測定する。IPv4に固定する場合はcURLにも明示し、実測IPの/32を許可する。IPv6を使うなら別途実測して/128を指定する。
4. 現行endpointと独立した試験endpointの利用可否を確認する。利用できなければ別の隔離経路を決めるまで既存endpointのOAuthを外さない。
5. Slackデモと診断入口の公開期限を確認する。診断は7日、Slackデモは初回配備から14日で失効する設計で、自動延長しない。

### B. URLとRPi署名認証

1. API・画像・静的ファイル・スキャナ・棚URLの生成を共通化し、直書きの/books等をprefix対応にする。Jinjaはurl_forを使用する。
2. /で動く現行環境と、/labook/で動く試験環境を設定で切り替えられるようにする。DBの相対画像パスへドメインを埋め込まない。
3. Pythonの署名部品をFlask実行前の検証へ組み込み、全業務ルートの前で検証する。認証済み主体を要求ごとに保持する。
4. 初期HMAC仕様は[gateway README](../gateway/README.md)のv1を使う。鍵ID・メソッド・上流パス/生クエリ・Content-Type・最終本文ハッシュ・時刻・nonce・主体を署名する。
5. 現行v1には公開origin/prefixのフィールドはない。公開origin/prefixは両端の固定設定で検証し、ブラウザのForwarded/X-Forwarded-*を信じない。署名項目を増やすなら仕様を版上げし、両言語のベクトル試験を更新する。
6. nonce DBは全Gunicornワーカーで共有し、一意制約で原子的に消費する。時刻差は初期±60秒、保存障害・設定欠落・再送は拒否。鍵は32バイト以上、試験と本番で分離する。
7. nginx/Gunicorn待受、旧port、LAN直アクセスを棚卸しし、本番切替後の認証迂回を閉じる。監視例外が必要ならngrokから届かないローカル専用入口に限定する。

### C. PHP認証ゲートと中継

1. 単独デモから認証部品を分離し、本番専用セッション・CSRF・許可判定を実装する。デモのセッションや試験DBを共有しない。
2. 同じSlack Appを使う場合も本番/試験の正確なcallbackを追加登録し、既存デモcallbackは試験中維持する。Client Secretはwww外に置く。
3. 上流originを単一HTTPS先に固定し、TLS検証必須・自動リダイレクト追跡なしとする。ユーザー入力による任意URL中継を作らない。
4. /labookを境界付きで除去し、上流パス・生クエリを決定する。パストラバーサル、CR/LF、曖昧なエンコードを両端で同じ基準により拒否する。
5. GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONSを必要に応じ保持する。不要なCORS許可は出さない。
6. ブラウザのCookie/Authorization/Forwarded/署名/主体ヘッダーを除去し、必要なAccept等だけ転送する。ngrok案内回避ヘッダーはPHP側で追加するが、認証の代用にはしない。
7. multipartはPHPで受信した項目とファイルから送信本文を再構成し、その最終本文とContent-Typeを署名する。PHP上限近辺のファイルと重複項目を試す。
8. hop-by-hopヘッダーを除去し、圧縮・Content-Lengthを実体に合わせる。上流Set-Cookie/CORSをそのまま渡さず、Locationは既知の内部URLだけ/labook/へ写像する。
9. 本文/応答サイズ・接続/総時間の上限を定め、障害502・時間切れ504を返す。413が403になる件を専用入口で解決または利用者向けに適切に扱う。更新を自動リトライしない。
10. 静的ファイルと画像も認証対象とし、初期応答はprivate, no-store。署名済みproxyと同じ固定prefixから生成する。

### D. 本番から隔離した結合試験

- RPiの別ディレクトリ・port・試験DB・別鍵を使用する。試験プロセスの起動で既存Gunicornを停止しない。
- さくらは独立した実ファイルの入口を使う。/labook-previewは旧Redirectの先頭一致に巻き込まれるため使わない。
- 独立ngrok経路へIP制限とHMACを適用し、PHP→ngrok→RPiを往復する。部品試験成功だけで本番切替可能と判定しない。
- 公開prefixは設定化し、まず試験prefixで全機能を確認する。本番の/labook/と/Lのルーティングは別途候補設定を検証する。

## 5. 本番切替の通過条件

- 認証: 未ログイン、既ログイン、別アカウント、対象外Workspace、期限切れ、ログアウト、state/nonce再送を試す。対象外の実アカウント試験と単体試験を区別する。
- 入力省略: 大学SSO後に本人確認できる。失敗時は公開OIDCの選択方式へ切替可能で、認証省略にはならない。
- CSRF: 全更新メソッド、表紙アップロード、ログアウトで拒否を検証し、拒否時にDBが変化しない。
- 中継: JSON、multipart、日本語/重複クエリ、圧縮、302/304/404/409/413相当/502/504、同時画像要求を確認する。
- 業務: 一覧・検索・ページ送り・追加・単件/一括更新・削除・貸出/返却・所有者/棚・表紙・スキャナ・既存外部連携を試験DBで確認する。
- URL: /labook/にAPI/静的/画像が収まり、/L/<code>からログイン後の棚復帰が成立する。公開応答にngrok URLが漏れない。
- 境界: 許可IP外を拒否。許可IPでも署名なし/改ざん/期限切れ/同時再送を拒否。LANと旧portからの迂回も閉じる。
- 運用: IP変更、上流停止、鍵切替、時刻ずれ、nonce保存障害で安全に失敗する。DBのバックアップ・復元と保守表示を確認する。
- WordPress: トップ、記事URL、wp-login、wp-admin、wp-json、既存画像/CSS/JS、他サービスの応答が維持される。
- Git: 個別設定・鍵・ログを未追跡に保つ。既存追跡ファイルの実ホスト直書きも別途テンプレート化する。ignore追加だけでは既追跡ファイルを保護できない。

## 6. ルーティングと切替

本番で新設する公開ファイルは/labook/index.php等の薄い入口だけ。
本体・vendor・設定・鍵・セッション・ログ・バックアップはwww外に置く。
WordPressと同一オリジンなので、WordPressのスクリプトから隔離する設計ではない。

.htaccess候補は旧laBook用Redirect 2本を除き、WordPress生成ブロックより前の独立ブロックへ入れる。
実ApacheでEND対応・ループ・クエリ保持を検証し、次を無検証で配備しない。

```apache
# BEGIN LABOOK GATEWAY
RewriteEngine On
RewriteRule ^(?:labook|L)(?:/.*)?$ labook/index.php [END]
# END LABOOK GATEWAY
```

PHPで/labook→/labook/を正規化し、/Lと/L/<code>のGET/HEADだけを同一サイトの/labook/L…へ転送する。
更新メソッドは405。/Library等を捕捉しない。更新要求に末尾スラッシュ転送を無条件適用しない。

1. 全通過条件を満たしてから、本番設定・.htaccess候補・所要停止時間・復旧手順を確認する。
2. 最新.htaccessの内容/ハッシュ/所有者/権限とDBバックアップをGit外へ保存する。準備後に原本が変われば候補を作り直し、第三者更新を上書きしない。
3. 新PHP本体・設定・依存関係を非公開領域へ配備。試験担当者にも通常のSlack認証を必須にし、公開バイパスを作らない。
4. laBookだけの短い保守時間に入り、RPi署名必須化 → ngrok送信元IP制限 → 保護の確認 → ngrok OAuth解除の順に進める。途中で未保護の公開状態を作らない。
5. .htaccessを所有者・権限を保って原子的に更新し、WordPressの代表URLを即確認する。WordPressは継続稼働させる。
6. 新Slack認証・中継・画像・棚URL・試験専用データの更新を確認し、保守表示を解除する。
7. 成功後、不要な診断入口・比較モード・試験callbackを整理する。公開期限のあるデモをそのまま本番に流用しない。

## 7. 復旧

- laBookだけの問題なら、新ゲートを保守表示または検証済みの別ログイン入口へ戻す。WordPressのDBや設定は復元しない。
- .htaccess起因でWordPressが壊れたら直ちに原本へ復旧する。途中の更新があれば差分で戻す。
- 旧Redirectを戻すだけでは、IP/署名制限が残る旧ngrokへブラウザが到達できず復旧しない。
- 旧方式へ戻す場合はngrok OAuthを先に再有効化して保護を確認し、その後に新IP制限/RPi署名必須化を旧状態へ戻し、最後に旧Redirectを復旧する。
- 旧3MAU制限で運用できなければlaBook保守表示を復旧先とする。認証を外して公開しない。
- IP変更は管理下で再測定し、非公開の許可IPを更新する。拒否IPの自動許可をしない。

## 8. 設定・成果物の保管

- Git管理候補: コード、空値/架空値のテンプレート、試験、手順書。
- Git外: SSH/サイト実パス、公開origin、SlackワークスペースURL/ID、Client ID/Secret、callback、ngrok endpoint/ポリシー、送信元IP、鍵ID/鍵、実行ログ・バックアップ。
- ローカルはdeploy/local/等のignore対象。さくらはwww外、RPiはリポジトリ外の専用設定で、所有者だけが読める権限にする。
- 実値をテストfixture、エラー、CI出力へ複製しない。コミット前にcheck-ignore、追跡一覧、ステージ差分を検査する。
- 秘密が既存履歴に見つかった場合は失効・再発行を優先し、共有履歴を書き換える作業は本移行と分ける。

## 9. 再開時の最初の作業

1. 引継ぎ要約と非公開設定の存在・期限を確認する。
2. RPiの接続先を確認し、現行構成を読み取り調査する。
3. 並行試験の通信経路を確保する。
